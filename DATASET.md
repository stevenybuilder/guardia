# DATASET.md — Mock Observability Dataset

The plugin ships with a hand-authored + algorithmically-generated observability fixture. **No external dataset dependency** — every record is narrative-first, stitched to real `tsre-microservices` method names, so Codex can cite specific incidents by ID.

## Source of truth

`src/main/resources/fixtures/datadog-fixtures.json` — **~6.2 MB, deterministic**. Regenerated by `scripts/generate-fixtures.py` (seed=20260418 → identical output every run).

```
$ python3 scripts/generate-fixtures.py
[ok] wrote .../datadog-fixtures.json
     services=12 incidents=2000 methods=15 events=10000 archetypes=35
```

CLI override: `python3 scripts/generate-fixtures.py --incidents 500` for a smaller corpus during iteration.

## Composition

| Entity | Count | Origin | What reads it |
|---|---|---|---|
| `services` | 12 | Hand-authored, tsre-microservices-aligned (payment, order, inventory, catalog, cart, user, shipping, recommendations, search, notifications, fraud, analytics) | Layer 1 heuristic (error rate, deps, deploy window) |
| `incidents` | ~2 000 | 4 hand-crafted demo incidents (INC-4402 null-check, INC-4417 retry storm, INC-4388 inventory race, INC-4213 webhook DLQ) + ~1 996 archetype-generated narratives drawn from a 35-pattern pool (null deref, race, unbounded retry, deadlock, conn/memory leak, N+1, cache stampede, TZ bugs, off-by-one, SQLi regression, deserialization, TLS expiry, rate-limit amplification, circular dep, stale cache, log token leak, CORS, pagination, param shadowing, mutable default, async callback, ReDoS, swallowed exception, logging recursion, field typo, enum drift, migration rollback, timeout cascade, idempotency, consumer lag, cold start, JWT drift, goroutine leak, config drift). Each carries title / description / root cause / offending code snippet (Java/Kotlin/Python/Go/JS chosen to match the service language) / keywords / severity. Dates span 18 months. | Layer 2 Codex (causal cross-reference, BM25 retrieval corpus) |
| `methods_of_interest` | 15 | Anchored to actual tsre source-file paths + line numbers | Wedge 1 gutter icon trigger |
| `events` | ~10 000 | Algorithmic over 30-day window: incident-clustered + baseline noise, weighted by service request volume. Only incidents inside the 30-day event window carry clustered events; older archetype incidents live as pure narrative. | Layer 1 rolling metrics + timeline UI |

## Why 2000 incidents × 10000 events

- **Codex retrieval stops being trivial.** With 20 narratives, BM25 recall was effectively 100% on any demo diff. At 2000 incidents the retriever actually has to discriminate, making the structural + BM25 + RRF pipeline (ARCHITECTURE.md §3) load-bearing instead of decorative.
- **Demo incidents still win retrieval.** The 4 hand-crafted incidents keep their method-specific keywords and offending code — they bubble to the top of RRF for the curated demo diffs while the archetype-generated corpus provides realistic lexical noise.
- **Bundle size still tractable.** ~6.2 MB JSON; parses in ~150 ms at plugin startup. Well under the 50 MB IntelliJ plugin-jar guideline.
- **Event:incident ratio ~5:1.** Preserves the prior distribution shape so Layer 1 rolling aggregates don't change character.

## Schema contract (abbreviated — full schema lives in the generator)

```jsonc
{
  "meta":                 { generated_at, seed, window_start/end, counts },
  "services":             [ { name, team, language, deps, error_rate_1h,
                               error_rate_delta_vs_last_commit, change_velocity_7d,
                               deploy_window_today, ... } ],
  "incidents":            [ { id, service, status, severity, opened_at, resolved_at,
                               title, description, root_cause, offending_commit,
                               offending_file, offending_methods, offending_code_snippet,
                               resolution, keywords } ],
  "methods_of_interest":  [ { fq_name, service, file, line, risk_hint,
                               linked_incidents, linked_events_30d } ],
  "events":               [ { id, timestamp, type, service, method, severity,
                               metric_name, metric_value, threshold, message,
                               related_incident_id } ]
}
```

Event `type` ∈ `metric_spike | alert_fired | span_error | deploy | saturation_warning | slow_query`.

## Runtime architecture

**JSON on disk + in-memory Kotlin indexes.** At plugin startup, `FixtureLoader` reads the JSON via `getResourceAsStream("/fixtures/datadog-fixtures.json")` and parses it with `kotlinx.serialization-json` (only new dep; already planned for Responses API I/O). `FixtureIndex` then builds 8 `HashMap` lookup indexes used by `MockDatadogService`:

- `servicesByName`
- `incidentsById`
- `incidentsByService`
- `incidentsByKeyword` (lowercased inverted index)
- `incidentsByOffendingMethod` (inverted index)
- `methodsByFqName`
- `eventsByService` (values sorted by timestamp)
- `eventsByIncidentId`

Rejected alternatives: SQLite, CSV, Parquet. Reason: zero judging upside, adds dependencies and demo risk. 848 KB fits comfortably in memory and loads in <50ms.

## What each layer reads

- **Layer 1 (Kotlin heuristic — `computeBaseline`):** `services[*].error_rate_1h`, `deploy_window_today`, `direct_dep_count`, `change_velocity_7d` + rolling aggregates over `events[*]` for touched services.
- **Layer 2 (Codex agent mode via `get_related_incidents`):** full `incidents[*]` records — especially `description`, `root_cause`, `offending_code_snippet`, `keywords` — to detect whether a PR diff re-introduces or addresses a past failure pattern.

## Changing the data

1. Edit `scripts/generate-fixtures.py` (new incident narrative, new service, different event distribution).
2. Re-run `python3 scripts/generate-fixtures.py`.
3. Commit both the script **and** the regenerated JSON (so the demo is reproducible without Python at judge-time).

**Do not hand-edit the JSON.** Generator is the source of truth.

## Post-hackathon path to real data

`RealDatadogService` (toggled by `USE_REAL_DATADOG` setting) replaces the fixture-backed `MockDatadogService` with calls to the official Datadog API — incidents, error tracking, service topology, monitors. Same `DatadogService` interface; one-line swap. The fixture shape mirrors the real API response shapes closely enough that no mapping layer is needed on Layer 1.
